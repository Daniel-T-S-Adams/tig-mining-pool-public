# Member-pool protocol v0

Status: settled contract for the testnet protocol spike  
Protocol version: `0.1.0`  
Last updated: 2026-08-07

This document defines the boundary between a member agent and the pool. It is
specific enough for the two sides to be implemented independently: it defines
identity, authentication, capacity offers, assignments, progress, artifact
handoff, acknowledgements, retries, version negotiation, and fault
classification.

The mining rules in [mining_system.md](mining_system.md) remain authoritative.
The TIG-facing contract is [tig_integration.md](tig_integration.md). The
security controls for authentication and hostile package handling are in
[security.md](security.md). The
machine-readable schemas for this version are under
[`schemas/member_protocol/v0.1.0`](../schemas/member_protocol/v0.1.0/README.md).

## 1. Scope and protocol shape

V0 uses HTTPS for every member-pool operation. Control messages are JSON.
Large proof material is one resumable binary upload using the package format
in section 10. A member never calls a TIG write endpoint and never receives a
TIG API key or signing key.

The protocol is asynchronous because TIG must confirm a precommit before an
assignment exists:

```text
enrol worker and register slot
    -> offer AVAILABLE capacity
    -> if pool capacity is full, wait in the renewable FIFO offer queue
    -> pool reserves slot and submits precommit
    -> worker keeps offer alive
    -> TIG confirms precommit and selected track
    -> pool publishes assignment
    -> worker acknowledges and computes every nonce
    -> worker packages and uploads all proof material
    -> pool receives, checks, and durably accepts package
    -> pool returns durable-acceptance receipt
    -> slot and member retention obligation are released
```

Pool-to-member state is obtained through offer, assignment, and upload status
reads and heartbeat responses. V0 does not require a permanently open socket.

## 2. Identities and ownership

All pool IDs are lowercase UUIDs generated by the party identified below.
They are opaque: clients must not infer ordering, identity, or authorization
from their contents.

| Identity | Issuer | Meaning and uniqueness |
|---|---|---|
| `member_id` | Pool | One registered pool account. It is never selected by the worker. |
| `worker_id` | Pool | One installed member agent, permanently scoped to one member unless an audited account-recovery action says otherwise. |
| `credential_id` | Pool | One Ed25519 public key authorized for a worker. More than one may exist briefly during rotation. |
| `slot_id` | Pool | One independently assignable CPU or GPU capacity unit belonging to one worker. |
| `client_slot_key` | Worker | Stable member-local identity of one logical slot across generations. Unique within a worker. |
| `slot_registration_id` | Worker | Idempotency identity of one initial registration or reconfiguration attempt. |
| `qualification_id` | Pool | One known-output qualification attempt bound to a slot generation and compute/runtime digest. |
| `fixture_id` | Pool | Immutable identity of the known-output execution used by one qualification task. |
| `qualification_result_id` | Worker | Idempotency identity of one submitted qualification result. |
| `offer_id` | Worker | Idempotency and identity of one capacity offer. Never reused for another availability period. |
| `assignment_id` | Pool | Pool-local identity of one confirmed TIG precommit assignment. |
| `benchmark_id` | TIG | TIG protocol identity. Permanently maps to exactly one assignment and member. |
| `event_id` | Worker | Idempotency identity of one assignment event. |
| `package_id` | Worker | Identity of one package-generation attempt for an assignment. |
| `upload_id` | Pool | Identity of one resumable upload session. |
| `receipt_id` | Pool | Immutable durable-acceptance acknowledgement. |

A slot represents the capacity that can execute one complete benchmark. A CPU
slot is a fixed group of logical cores that the agent will schedule together.
A v0 GPU slot is one NVIDIA device; multi-GPU machines register one slot per
device. The same physical core or GPU must not appear in two simultaneously
available slots.

`client_slot_key` identifies the same logical slot across reconfiguration; it
is not the write idempotency key. Initial registration uses a new
`slot_registration_id` and `prior_slot_generation = null`. Changing a slot's
architecture, core count, device, compute type, or qualified runtime inventory
uses a new `slot_registration_id`, names the current generation as
`prior_slot_generation`, atomically increments the generation, and requires
requalification. A stale prior generation conflicts. Reconfiguration is
forbidden while an offer, assignment, or upload is open.

A new registration ID with the current prior generation and unchanged compute
and runtime facts is a no-op that returns the existing generation and
qualification. It does not manufacture a new generation merely because a new
request ID was used.

An assignment is owned by the `member_id` through the permanent mapping:

```text
benchmark_id -> assignment_id -> slot_id -> worker_id -> member_id
```

Revoking a worker does not change this historical ownership.

## 3. Enrollment, authentication, rotation, and revocation

### 3.1 Initial enrollment

From an authenticated member account, the member creates a one-time enrollment
ticket. Account login and the user interface that creates the ticket are
outside this protocol; the ticket behavior is not:

- it is a cryptographically random, single-use bearer value with at least 256
  bits of entropy;
- it is stored by the pool only as a keyed hash;
- it is bound to one `member_id` and purpose `WORKER_ENROLLMENT`;
- it expires after 15 minutes; and
- consuming it and creating the worker are one transaction.

The agent generates an Ed25519 key pair locally and sends `EnrollRequest`. The
private key must never leave the member machine. It proves possession with an
unpadded base64url Ed25519 signature over this UTF-8 string with no final
newline:

```text
TIG-POOL-ENROLLMENT-V1
<enrollment_request_id>
<SHA-256 of the UTF-8 enrollment ticket as 64 lowercase hex characters>
<ed25519_public_key>
```

A successful response assigns `worker_id` and `credential_id`, records the
exact negotiated protocol version, and consumes the ticket. Retrying an
identical enrollment request with the same `enrollment_request_id` returns the
same response; changing any field for that ID is a conflict.

Slot registration is a separate authenticated call.
`slot_registration_id` is its idempotency key; `(worker_id, client_slot_key)`
locates the logical slot to create or reconfigure. A successful registration
returns a qualification ID and the digest of the exact generation, compute
facts, and runtime inventory that must qualify. A slot may offer work only
after the qualification flow in section 6 marks that exact digest
`QUALIFIED`.

### 3.2 Signed requests

Except for protocol discovery and initial enrollment, each request is signed
by an active worker credential and carries:

```text
X-Pool-Protocol-Version: 0.1.0
X-Worker-Id: <worker UUID>
X-Worker-Credential-Id: <credential UUID>
X-Request-Id: <new UUID for this HTTP attempt>
X-Request-Timestamp: <Unix time in whole seconds>
X-Body-SHA256: <64 lowercase hex characters>
X-Worker-Signature: <unpadded base64url Ed25519 signature>
```

`X-Body-SHA256` is SHA-256 over the exact transmitted request body. The empty
body uses SHA-256 of zero bytes. The signed byte string is UTF-8 with no final
newline:

```text
TIG-POOL-REQUEST-V1
<uppercase HTTP method>
<exact path, beginning with / and excluding scheme, host, and query>
<protocol version>
<worker_id>
<credential_id>
<request_id>
<request_timestamp>
<body_sha256>
```

V0 authenticated routes do not use query strings. IDs are path components and
filters are request bodies. The pool verifies the body hash and signature
before JSON decoding or allocating upload capacity.

The server accepts a timestamp within 300 seconds of server time and remembers
each `(credential_id, request_id)` for 24 hours. Reusing a request ID with
different signed bytes is rejected and audited. An HTTP retry normally uses a
new request ID but retains the message's application idempotency key such as
`offer_id`, `event_id`, or `package_id`.

The credential authorizes only its exact `worker_id` and that worker's slots,
offers, assignments, uploads, and receipts. Any worker ID in the path or body
must equal the signed header, and the pool derives `member_id` from its stored
worker binding rather than trusting a client claim. Cross-worker resource IDs
are rejected without disclosing whether the resource exists.

TLS authenticates the pool response. Every state-changing response contains
the application idempotency key and resulting resource identity. A lost
durable-acceptance response is recovered through upload or assignment status,
which returns the same immutable receipt.

An error echoes `request_id` when the request carried the standard signed
header, or `enrollment_request_id` for a decoded enrollment attempt. The public
protocol-discovery endpoint and failures that occur before either ID can be
decoded may omit both; server time and the machine error code remain required.

### 3.3 Credential rotation and recovery

For ordinary rotation, the worker creates a new Ed25519 key and sends a
`RotateCredentialRequest` signed by its current key. The request also proves
possession of the new key by signing the UTF-8 string below with the new key:

```text
TIG-POOL-ROTATION-V1
<worker_id>
<rotation_id>
<new_ed25519_public_key>
```

The pool creates a new `credential_id`; the old credential remains valid for a
server-declared grace period no longer than 10 minutes, then becomes
`REVOKED`. Repeating the same `rotation_id` and new public key returns the same
result. A different key for the same rotation ID is a conflict.

If the old private key is unavailable, the authenticated member account can
create a 15-minute `WORKER_RECOVERY` ticket bound to the existing `worker_id`.
Consuming it attaches a new key to that worker and revokes every old
credential. This preserves access to the worker's existing assignments without
changing ownership.

Consuming the ticket proves possession of the new key with an unpadded
base64url Ed25519 signature over this UTF-8 string with no final newline —
recovery has its own signing domain and never shares the enrollment or
rotation namespace:

```text
TIG-POOL-RECOVERY-V1
<recovery_request_id>
<SHA-256 of the UTF-8 recovery ticket as 64 lowercase hex characters>
<new_ed25519_public_key>
```

`recovery_request_id` is a new UUID and the idempotency identity of one
recovery attempt: repeating the identical request returns the recorded
result; different content for the same ID is a conflict. The ticket is
bound to its exact `worker_id` and rejected for any other worker. A worker
revoked as a security action cannot be recovered by this path; only an
explicit, audited pool decision reinstates it, after which ordinary
recovery applies. The HTTP route and schema for recovery, and the account
login that authorizes ticket creation, remain outside this protocol
version.

The member or an operator may revoke one credential or the whole worker.
Revocation takes effect on the next request and prevents new offers,
heartbeats, events, and uploads. It does not erase state or reassign a
benchmark. If revocation was accidental, account recovery may restore access;
if it was a security action, the pool decides explicitly whether any pending
assignment may continue. Authentication failures themselves do not count
against mining trust.

## 4. Version negotiation

`GET /member/v0/protocol` is public and returns the exact protocol and package
versions the server currently accepts. Enrollment sends the worker's supported
versions and package formats; the server selects and returns one exact common
protocol version and package format.

Every later message contains `protocol_version`. An exact supported version is
required; the server does not guess compatibility from SemVer. No common
version produces HTTP `426` and `INCOMPATIBLE_PROTOCOL`, with no state change.
Fields unknown to the selected schema are rejected.

Once an assignment is issued, the pool continues supporting its negotiated
version until that assignment is durably accepted or terminal. Removing a
version may prevent new offers but must not strand an existing assignment or
upload. A format change creates a new schema directory and version; it never
silently changes the meaning of `0.1.0`.

| `POST /member/v0/slots/{slot_id}/qualification/task` | empty object -> known-output task | `qualification_id` |

All state-changing JSON calls atomically store the idempotency key, canonical
body hash, and result. Repeating the same key and body returns the recorded
result. Repeating the key with a different body returns `409
IDEMPOTENCY_CONFLICT`. These records live at least as long as the affected
workflow and never expire while a retry could still be valid.

## 6. Compute-slot and capacity-offer contract

A registered slot records:

- `compute_kind`: `CPU` or `GPU`;
- `compute_type`: one exact TIG value allowed by the pinned integration;
- `cpu_arch`: `amd64` or `arm64`;
- CPU vendor and fixed logical-core count for CPU slots;
- NVIDIA device identity, one device per GPU slot, and reported NVIDIA driver,
  CUDA driver, and Container Toolkit versions;
- agent version, supported protocol versions, and runtime bundle version;
- digest-pinned runtime images available to the agent; and
- a pool-issued qualification ID and status.

The agent must report its observed facts. A label is not evidence of
compatibility; the pool checks them against the supported compute matrix and
qualification result.

The pool binds qualification to:

```text
qualification_spec_digest = SHA-256(RFC 8785 canonical JSON([
    worker_id,
    slot_id,
    slot_generation,
    compute,
    runtime_inventory
]))
```

Before canonical encoding, `available_image_manifest_digests` is sorted by
ascending UTF-8 byte order; it is a logical set, so sender array order cannot
change the digest.

The member fetches the qualification task for that digest. The task contains
one complete known-output execution: TIG settings, `rand_hash`, nonce,
hyperparameters, fuel budget, algorithm URL and SHA-256, runtime/verifier image
reference and platform digest, and the expected canonical output-record
SHA-256 and quality. The agent verifies the artifacts, runs `tig-runtime`, runs
`tig-verifier`, and submits the complete output record, quality, observed
runtime inventory, and timing under a new `qualification_result_id`.

The pool independently hashes the canonical result, compares the expected
quality and output, and verifies that the observed inventory and compute facts
still produce the qualification digest. Success changes that exact slot
generation to `QUALIFIED`; mismatch changes it to `FAILED` with a reason.
Tasks expire after 15 minutes. Retrying the same result ID and body returns the
same status. A new registration generation invalidates every older
qualification. Qualification establishes compatibility, not honesty, so a
failed qualification prevents capacity offers but does not count as a mining
trust failure.

A capacity offer is valid only with `slot_state = AVAILABLE`. It repeats the
current compute facts and qualification-spec digest so unexpected drift fails
closed. The pool handles it as follows:

1. Atomically reject another open offer or assignment for the slot.
2. Apply account status, tier, qualification, collateral, compatibility, and
   unresolved-exposure limits.
3. Enforce both `member_unverified < tier_number` and
   `pool_unverified < internal_pool_unverified_limit` before creating a
   precommit intent.
4. Return `NO_ACTION` or `REJECTED` without queuing when the member is not
   eligible for work.
5. If the member is eligible but only the pool-wide limit is full, reserve the
   local slot, return `QUEUED` with a renewable lease, and append the offer to
   the FIFO compute-availability queue. This creates no TIG write or financial
   reservation.
6. Otherwise reserve the slot and return `PENDING` with a renewable lease.
7. Record whether a TIG precommit has not started, is submitted, or is
   confirmed.
8. Publish an assignment only after the precommit is confirmed and the
   selected track is known.

V0 FIFO order is `(queue_accepted_at, offer_id)`. One member may have no more
than `max(0, tier_number - member_unverified)` queued or reserved offers, and a
slot may have only one. This prevents unused queue entries from exceeding the
work the member could legally receive.

If any live entry is already queued, a new eligible offer appends behind it
even if the global count has just fallen below the internal limit. Only the
queue promotion path may consume that newly open position.

When global capacity opens, the Controller selects the oldest eligible live
offer, re-runs every admission gate, and returns a short
`CONFIRM_AVAILABLE` directive with a fresh `ready_check_id`. The worker
confirms that the slot is still free by echoing that ID for the same `offer_id`
in its next signed heartbeat. Only that confirmation permits the atomic
capacity check, collateral reservation, and precommit intent. If the ready
check or ordinary offer lease expires, the pool removes the offer without a
member penalty and examines the next queue entry. Future trust-based queue
priority requires a new versioned policy; it is not part of v0.

The worker heartbeats a pending offer every 30 seconds. The server returns an
explicit `lease_expires_at`; the spike default is 90 seconds from the last
accepted heartbeat. If the lease expires before a precommit is submitted, the
offer is cancelled without trust effect. Once the pool records
`PRECOMMIT_SUBMITTED`, the member's commitment is irrevocable: a missing
heartbeat marks the worker unreachable but does not silently reassign the TIG
benchmark.

The same slot cannot make another offer while it is `RESERVED`, `COMPUTING`,
`PACKAGING`, or `UPLOADING`. Other independently registered slots on the same
worker may continue.

This bounds pre-acceptance exposure to one benchmark per slot. After durable
acceptance the slot may offer again, but the accepted benchmark continues to
count toward the tier's unverified limit until TIG verifies it or records a
terminal stopped, expired, or failed outcome. Method-verification collateral
may remain reserved after tier concurrency is released.
Initial offer admission is only a preliminary check: after the pool proposes
all track settings, it must reserve the maximum bundle-scaled financial
exposure defined in [accounting.md](accounting.md) before submitting the
precommit. Failure to reserve cancels the pending offer without a TIG write.
The tier joining fees, failure charge, and global headroom remain versioned
policy values; absence of an applicable policy produces `NO_ACTION`, never
unlimited work.

## 7. Confirmed assignment contract

The assignment embeds the confirmed TIG precommit, not the pool's proposed
settings. Its identity-critical body contains at least:

- protocol, package-format, network name, TIG API base URL, and pool-player
  identity;
- `assignment_id`, `offer_id`, `member_id`, `worker_id`, `slot_id`, exact slot
  generation, complete qualified compute specification, qualification ID, and
  qualification-spec digest;
- TIG `benchmark_id`, decision block, confirmed block, challenge, algorithm,
  selected track, hyperparameters, fuel, bundle count, nonce count,
  `rand_hash`, compute type, and `block_started`;
- exact nonce range `[0, num_nonces)`;
- algorithm binary SHA-256;
- challenge runtime/verifier image manifest digest and platform;
- upstream TIG commit and Merkle algorithm version; and
- package format and assignment-specific resource limits.

The pool returns this data as `assignment_identity` plus:

```text
assignment_digest = SHA-256(RFC 8785 canonical JSON(assignment_identity))
```

Expiring download URLs, display names, heartbeat timing, and estimated wall
times are outside the identity object. The agent must recompute and compare the
digest, verify every downloaded binary/image against its digest, and refuse to
start if any identity field is inconsistent. In particular, confirmed
precommit `compute_type` must equal `compute.compute_type`, the runtime platform
architecture must equal `compute.cpu_arch`, and the qualification ID and digest
must cover the stated slot generation.

The pool supplies `ack_by`, `workflow_expiry_block`, `proof_reserve_blocks`,
`package_due_before_block`, and a non-authoritative UTC estimate. For the
protocol spike these are derived exactly as:

```text
workflow_expiry_block = block_started + 120
proof_reserve_blocks = 10
package_due_before_block = workflow_expiry_block - proof_reserve_blocks
```

The package must reach `DURABLY_ACCEPTED` while the pool's latest confirmed
height is strictly less than `package_due_before_block`. The ten reserved
blocks are pool-owned time for benchmark commitment confirmation, TIG sampling,
proof construction, proof submission, and confirmation before local expiry.
If an assignment would be published at or after its package deadline, the pool
must not publish it as executable work.

Block height and current server state are authoritative; the UTC deadline is
display-only. Ten is a spike constant to be replaced with a reviewed value
from measured confirmation and proof timings. V0 does not use a runtime
estimate to resize the benchmark.

The worker acknowledges within 60 seconds, then executes every nonce exactly
once using the confirmed assignment. Failure to acknowledge does not by itself
prove member fault; the pool keeps the reservation and classifies the eventual
outcome using section 15.

## 8. Heartbeats, progress, completion, cancellation, and errors

While an offer or assignment is open, the worker sends a heartbeat every 30
seconds. A heartbeat reports the slot's observed state, assignment IDs, last
accepted event sequence, and upload offsets. The response returns server time,
authoritative states, lease expiry, and directives such as `CONTINUE`,
`CANCEL`, `REAUTHENTICATE`, or `UPGRADE_REQUIRED`.

Assignment events have a strictly increasing `event_seq` starting at 1 and a
unique `event_id`. They are facts from the agent, not authority to advance TIG
state. The defined event types are:

- `PROGRESS`: current stage plus completed and total nonce counts;
- `COMPUTE_COMPLETED`: all nonces have outputs and qualities locally;
- `PACKAGE_STARTED`: package construction began;
- `PACKAGE_READY`: package checksum and declared sizes are known;
- `RETRYABLE_ERROR`: a typed problem the worker is retrying; and
- `TERMINAL_ERROR`: the worker cannot finish without intervention.

Duplicate event IDs return the original acceptance. A sequence lower than the
last stored sequence is a harmless duplicate only if its event ID and body
match; otherwise it is rejected. A gap is rejected with the expected sequence
so the worker can replay missing events.

A member cancellation is a request, not an immediate local rewrite. Before a
precommit is submitted, the pool may accept it without trust effect. After
submission, the pool records the reason, preserves ownership, and decides the
terminal classification. A pool `CANCEL` directive includes whether the reason
is pool, TIG, security, or member attributed. The member must stop safely and
retain any already-created artifact until the pool returns a terminal state or
explicitly releases it.

Missing heartbeats and transient connection failures are operational signals,
not trust penalties. The decisive member deadline is failure to deliver a
durably acceptable package before `package_due_before_block`, subject to pool
and TIG outage evidence.

## 9. Member-side lifecycle and slot release

The member-visible assignment state is:

```text
OFFER_QUEUED -> OFFER_READY_CHECK -> OFFER_PENDING
               or
AVAILABLE offer ------------------> OFFER_PENDING
    -> ASSIGNMENT_AVAILABLE
    -> ACKNOWLEDGED
    -> COMPUTING
    -> PACKAGING
    -> UPLOADING
    -> PACKAGE_RECEIVED
    -> PACKAGE_STRUCTURALLY_ACCEPTED
    -> PACKAGE_DURABLY_ACCEPTED
```

Terminal branches are `CANCELLED`, `EXPIRED`, and `FAILED`. Pool-side TIG
states after durable acceptance remain visible for status but do not occupy
the slot and do not create a member proof-serving obligation.

The slot transitions are exactly:

```text
AVAILABLE -> QUEUED -> RESERVED -> COMPUTING -> PACKAGING -> UPLOADING -> AVAILABLE
AVAILABLE ----------> RESERVED -> COMPUTING -> PACKAGING -> UPLOADING -> AVAILABLE
```

For v0, the member may not offer the same slot while its package uploads in the
background. The slot returns to `AVAILABLE` only when the durable-acceptance
receipt is committed. At that instant the receipt sets both:

```text
member_may_delete_package = true
slot_released = true
```

The member should persist the receipt before deleting its local package. If
the response is lost, it retrieves the same receipt from status. `RECEIVED` or
`STRUCTURALLY_ACCEPTED` never releases the slot or retention obligation.

## 10. Proof-material package v1

### 10.1 Serialization

The media type is:

```text
application/vnd.tig-pool.proof-material-v1.tar+zstd
```

It is one POSIX `ustar` archive compressed as one Zstandard frame. The archive
contains exactly four regular files at its root, in this order:

```text
manifest.json
qualities.i32le
leaf-hashes.bin
outputs.ndjson
```

No directory, duplicate name, absolute path, `..`, backslash, link, device,
FIFO, sparse entry, PAX header, GNU extension, or extra entry is allowed.
File modes, owners, and timestamps have no meaning and are ignored. The tar
must end normally with zero blocks and contain no non-zero trailing data.

The Zstandard frame must declare content size, use no dictionary or skippable
frame, enable the frame checksum, use a window no greater than 64 MiB, and
contain no trailing frame or data. The member compressor must set that bound;
the pool rejects a frame that exceeds it. The pool parses and hashes the frame
as a bounded stream into quarantine; it never calls a general-purpose archive
extractor on a member-selected path.

### 10.2 Logical contents

`manifest.json` is UTF-8 RFC 8785 canonical JSON with no BOM or trailing
whitespace and conforms to `package-manifest.schema.json`. It binds the package
to the assignment digest, every identity, exact slot generation and compute
specification and qualification digest, the nonce range, the file lengths and
SHA-256 values, the expected Merkle root, and all relevant versions.

`qualities.i32le` contains exactly `num_nonces` signed 32-bit little-endian
qualities in ascending nonce order. Its length is exactly `4 * num_nonces`.

`leaf-hashes.bin` contains exactly `num_nonces` consecutive 32-byte TIG Merkle
leaf hashes in ascending nonce order. Its length is exactly
`32 * num_nonces`.

`outputs.ndjson` has exactly one canonical JSON object and one LF byte per
nonce, in ascending order with no blank lines. Each object conforms to
`output-record.schema.json` and contains:

```text
nonce
runtime_signature
fuel_consumed
solution
cpu_arch
```

`fuel_budget`, `runtime_signature`, and `fuel_consumed` are canonical
unsigned-64 decimal strings on the member boundary so no JSON implementation
can round them; the pool parses them to TIG unsigned integers before TIG use or
before reproducing `OutputData`. Other member-protocol JSON integers are
restricted to the exact IEEE-754 integer range. Values outside that range must
move to a decimal-string field in a later schema version, not be rounded.

The pool parses all output records and reproduces each TIG `OutputData`
metadata hash using the pinned upstream serialization. It compares every hash
with `leaf-hashes.bin`, reconstructs the TIG Merkle tree over the ordered leaf
hashes, and compares the root with the manifest. The output records are the
proof leaves; the complete ordered leaf-hash array is sufficient Merkle
material to construct the branch for any sampled nonce. The package therefore
supports a later sample without the member reconnecting.

These are mechanical identity, coverage, and consistency checks. They do not
decide whether a solution is semantically valid.

### 10.3 Maximums

Every assignment returns limits no greater than these protocol ceilings:

```text
compressed package:          64 GiB
uncompressed tar stream:    128 GiB
manifest.json:              256 KiB
one outputs.ndjson record:   16 MiB including LF
tar entries:                 exactly 4
filename length:             64 ASCII bytes
upload chunk:                 1-64 MiB
```

The pool may advertise lower limits based on the selected challenge and its
available storage. The member must reject an assignment if the advertised
limits cannot hold a valid result it is expected to produce. The pool rejects
the package before durable acceptance if a declared or observed value exceeds
the assignment limit. It enforces compressed and uncompressed counts during
streaming, not after extraction.

## 11. Resumable and idempotent upload

After `PACKAGE_READY`, the worker creates an upload by declaring
`package_id`, assignment digest, media type, compressed and uncompressed sizes,
manifest SHA-256, and whole-package SHA-256. The server checks limits and
returns `upload_id`, the committed byte offset, a chosen chunk size, and an
expiry no later than the assignment deadline.

Each `PUT /member/v0/uploads/{upload_id}` has a raw body and these additional
headers:

```text
Upload-Offset: <zero-based decimal byte offset>
Upload-Chunk-SHA256: <64 lowercase hex characters>
Content-Length: <chunk bytes>
Content-Type: application/octet-stream
```

The normal offset must equal the server's committed offset. The server hashes
and durably commits a chunk before returning the next offset.

- If an offset equals the current offset, the chunk is appended once.
- If an offset is lower and the exact range and checksum were already
  committed, the server returns the current offset without writing again.
- If that older range differs, the upload fails with `CHUNK_CONFLICT`.
- A higher offset returns `OFFSET_MISMATCH` and the current offset.
- Bytes beyond the declared package size are never accepted.

The worker may query status and resume at the returned offset after any lost
response. Starting the same `package_id` with identical declarations returns
the same live upload. Changed declarations conflict. Only one package can
become durably accepted for an assignment; rejected package generations remain
auditable but may be replaced with a new `package_id` before the deadline.

After every byte is present, finalize compares the whole compressed SHA-256.
Finalization is idempotent and starts the bounded structural-ingestion job.

## 12. Received, structurally accepted, and durably accepted

The states have deliberately different meanings:

`RECEIVED`
: All declared compressed bytes are in quarantine and the compressed size and
  whole-package SHA-256 match. The archive has not yet earned trust and may not
  be the authoritative artifact.

`STRUCTURALLY_ACCEPTED`
: Bounded decompression and parsing succeeded; the manifest and assignment
  match; there are exactly four safe entries; nonce coverage and ordering are
  exact; file lengths and hashes match; qualities decode; output records have
  valid shapes; every leaf hash reproduces; and the calculated Merkle root
  matches. The accepted object and database pointer are not yet necessarily
  committed together.

`DURABLY_ACCEPTED`
: The immutable artifact is published in the configured temporary artifact
  store, a read-after-write or equivalent durability check succeeded, and one
  database transaction recorded its location, hashes, size, format, retention
  state, assignment state, slot release, and immutable acceptance receipt.

Only `DURABLY_ACCEPTED` permits the pool to submit the TIG benchmark commitment.
Only its receipt permits the member to delete local proof material or offer
the slot again.

If processing fails before durable acceptance, status returns a stable typed
reason. The member retains its package and may retry or create a corrected
generation. If the pool loses an artifact after issuing the receipt, it is a
pool failure and cannot be charged to the member.

## 13. Retry, timeout, and clock rules

Control requests use a 5-second connection timeout and 30-second total timeout.
Upload chunks use a 5-second connection timeout and 120-second total timeout.
On network failure, `408`, `429`, or `5xx`, the member retries with full-jitter
exponential backoff beginning at 1 second and capped at 30 seconds. It honors
`Retry-After`. There is no small fixed retry count for an idempotent operation;
retry continues until success, an authoritative terminal response, upload
expiry, or the assignment deadline.

Other `4xx` responses are not blindly retried:

- `401`/`403`: correct clock or credential state, then reauthenticate;
- `409`: fetch authoritative resource state and reconcile;
- `413`: package exceeds the assignment contract and cannot be retried
  unchanged;
- `422`: correct the message or package before retrying; and
- `426`: use a supported negotiated version without rewriting an open
  assignment to a different package version.

Server time and TIG block height are authoritative. Member wall clocks are
used only for request freshness and display. `GET /member/v0/protocol` returns
server time so a client can diagnose skew. Heartbeat leases and assignment
responses contain absolute server times; block deadlines remain authoritative
even if wall-clock estimates drift.

## 14. Incompatible clients and fail-closed behavior

The pool creates no precommit unless the worker, slot, credential, protocol,
runtime inventory, and qualification are all compatible. If incompatibility
appears after a precommit:

- the assignment remains permanently bound to its original version and
  member;
- the server keeps that schema and upload parser available for the workflow;
- the member stops before computation if an identity digest or binary/runtime
  digest is wrong;
- the pool returns a typed error and never substitutes a different algorithm,
  track, binary, runtime, or benchmark under the same assignment; and
- an operator resolves any case that cannot be safely reconciled.

An unknown enum, missing required field, lossy integer, invalid digest, or
schema mismatch is incompatible input, not a value to coerce.

## 15. Failure attribution and trust effects

Every terminal outcome records one of `MEMBER`, `POOL`, `TIG`, or `UNRESOLVED`
plus a machine reason and evidence. Only published chargeable tier-failure
reason codes increment `f`; a `MEMBER` method-verification outcome instead uses
the separate method-loss rule unless another chargeable failure also occurred.
The explicit zero-verification-quality capacity rule below may increment `f`
without alleging fraud. V0 has no general mining trust score.

| Event | Attribution |
|---|---|
| Package bytes match the declared checksum but its identity, coverage, structure, leaf hashes, or Merkle root are wrong | `MEMBER` |
| Wrong binary/runtime used, missing or duplicate nonce, or TIG confirms non-reproducible/fraudulent member output | `MEMBER` |
| Member cancels after precommit or misses the package block deadline while pool and TIG services were available | `MEMBER` |
| Complete benchmark has zero bundles meeting TIG's minimum verification quality | No fraud attribution; chargeable tier failure unless a pool/TIG/compatibility incident applies |
| TIG verifies the benchmark but its bundles earn no qualifiers | No failure |
| Pool stops an otherwise valid complete benchmark for a pool/TIG reason | No member failure |
| Slot fails or times out during pre-assignment qualification | No mining-trust effect; slot remains ineligible |
| Authentication failure, duplicate request, stale request timestamp, lost heartbeat, or transient member network error by itself | No trust effect |
| Pool issued an assignment inconsistent with confirmed TIG data | `POOL` |
| Pool rejected a structurally valid package, was unavailable for the upload window, or lost data after receipt | `POOL` |
| Pool constructed/submitted a wrong proof or missed a TIG submission after durable acceptance | `POOL` |
| Confirmed TIG outage or TIG state failure independent of both parties | `TIG` |
| Corruption origin, deadline availability, or semantic-failure origin cannot be established | `UNRESOLVED` |

A checksum mismatch in transit is retried and investigated; it is not a member
penalty until the received bytes are stable and evidence establishes a
member-originated bad package. Security violations such as forged signatures,
credential probing, or deliberate resource abuse are handled by account
security and may cause suspension, but they are separate from benchmark-failure
statistics.

## 16. Required invariants

1. One open assignment occupies exactly one slot, and one TIG benchmark has
   exactly one member owner.
2. A slot may offer capacity only with a successful qualification for its exact
   current generation, compute facts, and runtime inventory.
3. Registration, qualification, and capacity-offer retries cannot create an
   extra slot generation, qualification result, precommit, or reservation.
4. An assignment contains only confirmed TIG precommit facts.
5. The assignment digest binds the qualified slot generation and every fact
   capable of changing benchmark output or proof construction.
6. The spike package deadline preserves ten complete blocks before local
   workflow expiry for pool-owned protocol completion.
7. The package covers exactly `[0, num_nonces)` in ascending order.
8. A package retry cannot create a second accepted artifact.
9. `RECEIVED` and `STRUCTURALLY_ACCEPTED` release nothing.
10. A durable receipt is immutable, recoverable, and releases both local
   retention and the compute slot.
11. The pool can construct any sampled proof without the member after issuing
   that receipt.
12. No request retry can cause a duplicate assignment, event, upload byte
    range, durable acceptance, or TIG submission.
13. Missing connectivity alone never becomes a trust penalty.
14. Protocol incompatibility fails closed without changing assignment meaning.
15. A queued offer consumes neither TIG unverified capacity nor member
    collateral, and no queued promotion can bypass a fresh atomic global-limit
    and tier-limit check.
16. Tier removal or repurchase never releases an outstanding benchmark,
    reservation, fine, or method-verification exposure.

## 17. Decisions left to later documents

This protocol deliberately does not choose the account-recovery HTTP route and
schema (the recovery proof itself is specified in section 3.3), deposit
custody details, numerical `J[k]`/`X`/global-headroom values, relational
schema, artifact-store product, deployment topology, or production retention
capacity.

The member website login mechanism, which this section previously also left
open, **is now chosen**: the member connects a wallet and proves control of
its Base address, and that address is the member account (ADR 0011). §3.3's
`WORKER_RECOVERY` ticket is therefore authorized by a wallet signature. There
is no recovery of the account itself, so a member who loses their wallet also
loses the authority that issues those tickets.
Those choices may implement this contract but may not weaken its ownership,
idempotency, durable-acceptance, or failure-attribution rules.

The selected v0 database, storage products, process topology, and responsibility
boundaries are recorded in [architecture.md](architecture.md). They remain
behind this storage-neutral member contract.
